# 模擬ヒアリング計画 —— ①工場レイアウト最適化 PoC の見直し

**目的**：実際の企業へのヒアリングができていないので、**ChatGPT に発注側の担当者を演じてもらい、
ヒアリング → 要件の見直し → 作り直し**の流れを一度通す。

**元の依頼**：クラウドワークス テック「工場建設時のレイアウト設計最適化アルゴリズム PoC」
（建設業の顧客向け。入庫 → 製造 → 出庫の流れを満たすレイアウトを**複数提案する仕組み**）

---

## 0. 先に決めておくこと（いちばん大事）

**これは架空のヒアリングであると、成果物に必ず書く。**

- README とヒアリングメモの冒頭に「**ChatGPT に発注者役を依頼した模擬ヒアリングです。実在の企業ではありません**」と明記する
- **本物のヒアリング実績として見せない。** 提案時にも「模擬」と言う
- ChatGPT の答えは**架空の顧客の要望**であって、業界の事実ではない。
  法規・安全基準など**現実の根拠が要る話は、別途調べる**（または「未確認」と書く）

**この1行があるかないかで、ポートフォリオの信用が変わる。** 隠すより出したほうが強い。

---

**演じてもらう相手（2026/9/28に決定）：建設会社の設計提案チームの担当者。**
元の依頼の発注者と同じ立場なので、聞いた内容がそのまま「この依頼に答えられるか」の答えになる。

## 1. ChatGPT に渡す指示文（そのまま貼る）

```
あなたは、工場の設計・建設を請け負う建設会社の「設計提案チーム」の担当者です。
私は、御社から「工場レイアウト設計の最適化ツール（PoC）」の開発を相談された外部のエンジニアです。
これから私がヒアリングをするので、担当者として答えてください。

【あなたの設定】
・顧客は、新工場を建てる製造業の会社（食品・金属加工など、具体は自由に決めてよい）
・今はレイアウト案を手作業で作っている。案を作るのにも、条件を変えてやり直すのにも時間がかかる
・社内にプログラマはいない。ツールは設計担当者が自分で触る

【守ってほしいこと】
1. 担当者として一貫した立場で答える。設定は途中で変えない
2. 私が聞いていないことまで、先回りして全部は言わない。聞かれたことに答える
3. ただし、現場として当然の前提（安全・法規・作業動線など）は、聞かれたら具体的に答える
4. 数字は具体的に答える（面積、エリア数、案の数、待てる時間、頻度など）
5. 分からないことは「社内で確認します」と答えてよい。無理に作らない
6. 技術的な作り方はこちらに任せる。あなたは業務の要望を話す

最初に、この案件の背景と困っていることを3〜5行で話してください。
そのあとは、私の質問に1問ずつ答えてください。
```

**役を外して感想を聞きたくなったら、`（ここから素のChatGPTとして）` と前置きする。**

## 2. 聞く順番（3回に分ける）

1回で全部聞こうとしない。**1回30分・3回に分ける**と、頭が整理できる。

| 回 | 聞くこと | 目的 |
|---|---|---|
| **1回目** | 今どうやっているか（現状把握） | 何に困っているかを、自分の言葉で書けるようにする |
| **2回目** | 条件と評価（仕様の中身） | 今の PoC の制約が、実際に許されるかを確かめる |
| **3回目** | 使い方と運用（誰がどう使うか） | 画面と出力の形を決める |

## 3. 質問リスト

**今の PoC の制約から逆算して作ってある。** 答えがそのまま「直すか・直さないか」の判断材料になる。

### 1回目：現状把握

- 今、レイアウト案は**誰が・何を使って**作っていますか
- 1案作るのに**どれくらい時間**がかかりますか。**何案**作りますか
- 条件を1つ変えると、どれくらいやり直しになりますか
- 作った案は**誰が見て、何で決めますか**（社内会議／顧客提示）
- 今のやり方で、**いちばん困っているのはどこ**ですか

### 2回目：条件と評価（PoC の制約に直結）

| 質問 | 今の PoC | 確かめたいこと |
|---|---|---|
| 工場の形は長方形だけでよいですか。L字や柱・既存設備はありますか | 長方形のみ | 形の前提が崩れないか |
| エリアの数は6個で足りますか。実際はいくつですか | **6個固定** | 可変にする必要があるか |
| エリアは**回転**しますか（縦長・横長の入れ替え） | 回転なし | 探索の幅が変わる |
| **通路**は必要ですか。幅は何mですか | 扱っていない | 大きな追加要件になりうる |
| 「隣接させたい」「離したい」条件は、**何組くらい**ありますか | **各1組まで** | 複数対応が要るか |
| 隣接・離隔のほかに、**必ず守る条件**はありますか（搬入口の位置、危険物、温度、法規など） | なし | 判定ルールの追加 |
| 良し悪しは**動線の長さだけ**で決めてよいですか | 動線距離のみ | 評価軸が増えるか |
| 工程ごとに**運ぶ量の差**はありますか（重み付け） | 重みなし | 距離×量の計算が要るか |
| **最適解でなくてよい**ですか。「条件を満たす良い案が複数」で足りますか | 最適解は保証しない | 前提の確認 |
| 探索は**何秒まで**待てますか | 未定 | 打ち切りの基準 |

### 3回目：使い方と運用

- ツールは**誰が触りますか**（設計担当者／事務／外注）。PCの環境は
- 入力は**何から**持ってきますか（紙／Excel／CAD）
- 出力は**何案**必要ですか。**3案で足りますか**
- 図はどの形で欲しいですか（画面で見る／PDF／CADに取り込む）
- 案を見比べるとき、**数字は何が見たい**ですか（距離・面積・コスト換算）
- 顧客に見せるのは**どの形**ですか
- 使う頻度は（案件ごと／月に何回）

## 4. 聞くときの注意

- **自分で答えを言わない。** 「〜ですよね？」ではなく「〜はどうなっていますか？」
- **はい／いいえで終わらせない。** 終わったら「具体的には？」「たとえば？」を足す
- **数字を必ず聞く**（何個・何分・何案・何m）。数字が仕様になる
- **その場で「できます」と言わない。** 持ち帰って、できることとできないことを分ける

## 5. ヒアリングのあとの流れ

1. **`docs/ヒアリングメモ.md`** に、聞いた内容をそのまま書く（自分の解釈は分けて書く）
2. **`docs/要件定義_v2.md`** を作る。v1（今の PoC）から**変えるところだけ**を表にする
3. 変更を**3つに分ける**
   - **今すぐ直す**（半日で終わる・効果が大きい）
   - **次の版で直す**（README の「今後の改善」に書く）
   - **やらないと決める**（理由を書く。ここが一番大事）
4. 直したら**テストを足してから**実装する（今の128件を壊さない）
5. **README を更新**：模擬ヒアリングをした事実／分かった要望／対応したこと／見送ったことと理由

**「聞いた → 全部作った」ではなく「聞いた → 選んだ → 理由を書いた」が、いちばん評価される形。**
9/8のリサーチで見た発注者の条件「**仕様書が完全でなくても目的から考えられる**」は、まさにこれ。
